# Moor product map

Moor is a self-hosted Docker control panel for one server, serving an individual developer/operator and the agents acting for them. Its core loop is deploy, inspect, act, and adjust: run containers from GitHub source or registry images, diagnose their behavior, and maintain the Moor installation. Typical workloads include scrapers, workers, cron jobs, processing pipelines, and long-running scripts.

## Boundary and direction

Moor owns project configuration, container lifecycle orchestration, execution and schedules, operational history, domain-route configuration, and maintenance of its own installation. The HTTP API owns business logic and SQLite state; Docker owns image builds and container execution. Caddy provides reverse proxying and HTTPS for configured project domains. Operators supply the server, Docker Engine and Compose, source repositories/images, and DNS records.

The product stays single-server and single-operator: no cluster scheduling, multi-server fleet management, team/RBAC workflows, managed database service, or general PaaS. Containers can expose web endpoints and persist database files, but Moor does not take responsibility for application availability or database administration. Its DB backup feature snapshots Moor's SQLite state locally; it does not back up project volumes or provide offsite recovery.

Admin sessions and API keys grant host-equivalent authority through the Docker socket, not tenant isolation. The supplied Compose installation binds admin access to loopback; public project domains are separate. See [self-hosting](docs/self-hosting.md) and [docker-compose.yml](docker-compose.yml).

Current direction, established in [architecture](docs/architecture.md) and the [agent workflow](docs/agent-workflow.md): make single-server deployment and upkeep practical for agents, keep business logic in the API, and expand CLI coverage from demonstrated workflow needs. Drain, backups, cleanup, and self-update are core capabilities. The web console remains deliberately partial; full UI parity is not a goal.

## Surfaces and ownership

- `apps/api/`: authoritative HTTP API, SQLite state, Docker integration, and maintenance orchestration. `apps/respawner/` performs the transient Compose self-update and rollback work.
- `packages/contract/src/`: shared types, request validators, and HTTP client. `packages/cli/src/commands/` and `packages/mcp/src/tools/` adapt API operations for operators and agents. MCP currently uses stdio; CLI and MCP coverage differ.
- `apps/web/src/`: project and server monitoring, common deployment/configuration actions, logs, terminals, and cron. Advanced configuration and maintenance primarily use API/CLI/MCP.
- `apps/site/public/`: public marketing site and installer, not the admin console.

## Boundary wording to reconcile

[brand.md](brand.md) still excludes audit trails and SSL certificate management; current code records update/cleanup audits and integrates Caddy HTTPS. These are operational records and delegated TLS, not a team audit/compliance product or independent certificate service. Its blanket exclusion of databases/production web apps also needs qualification alongside [self-hosting](docs/self-hosting.md), which explicitly describes database directories as a volume use case. Generic container support does not imply managed-service responsibility. Reconcile the brand wording with these shipped mechanics while preserving the single-operator, single-server boundary.
